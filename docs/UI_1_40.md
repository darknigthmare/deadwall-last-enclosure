# Carnet et annexes — 1.40

## Navigation au clavier

Trois pertes de focus ont été reproduites dans le HTML livré de la 1.39 :

- **SÉCURISER** une annexe remplaçait le bouton focalisé par un bouton désactivé ; le focus restait lié à l’ancien nœud retiré.
- **CHOISIR COMME REPÈRE** reconstruisait le carnet régional sans focaliser le nouveau bouton du même lieu.
- Changer l’annotation d’un lieu reconstruisait son sélecteur sans lui rendre le focus.

`src/world-evolution-ui.js` rend le focus à l’onglet courant lorsque l’action renouvelée n’est plus utilisable. `src/frontier-ui.js` retrouve le bouton par son identifiant ou le sélecteur par son lieu. Si un filtre retire le lieu, le champ de recherche devient le contrôle de repli. Un focus déjà placé hors de la liste n’est pas déplacé.

## Boutons et transactions des annexes

Les boutons **SÉCURISER** ne vérifiaient que l’absence de district déjà sécurisé. Ils restaient donc activés avec un palier insuffisant, des stocks insuffisants ou pendant une sortie régionale, alors que le contrôleur refusait silencieusement l’action. Après sécurisation, les boutons **+ Bâtiment** ne vérifiaient que le nombre d’emplacements.

`src/world-evolution.js` expose maintenant `previewDistrictClaim` et `previewDistrictBuild`. Les transactions utilisent ces mêmes devis au moment de payer. L’interface désactive les actions refusées et affiche leur raison ; lorsqu’une action est disponible, son coût apparaît sur la carte. Les devis sont transitoires et ne sécurisent ni ne construisent rien.

L’ordre des conditions, les paliers, les coûts, les huit emplacements, les fonctions de sauvegarde et l’avancement des annexes sont conservés. Le coût de sécurisation reste la formule historique ; les coûts de bâtiments viennent du même catalogue de `core.js`. Les objets de coût renvoyés sont des copies : modifier un devis consulté ne modifie pas la prochaine transaction.

## Vérification

`tests/ui140.test.cjs` charge les scripts dans l’ordre du HTML livré. Les boutons et sélecteurs sont réellement montés dans cette fixture. Le DOM commun ne déclenche pas la propriété native `onclick` : l’activation du bouton Monde la déclenche explicitement dans le test. Ce modèle n’est pas un navigateur.

La fixture d’annexe utilise un palier et des stocks préparés ; la fixture de carnet charge deux lieux déjà repérés via une sauvegarde validée. Elles servent à vérifier ces parcours d’interface, sans prétendre représenter une campagne humaine complète.

Les sept scénarios couvrent les trois pertes de focus, un focus extérieur conservé, un district bloqué par le palier, le devis et les refus de stocks sans mutation, puis la construction d’une annexe par son bouton. Le dernier scénario vérifie le paiement unique, l’absence d’avancement sous la pause, le démarrage du chantier après fermeture du commandement et sa reprise avec les mêmes stocks et progression.

La reproduction utilise directement la source **1.39** en lecture seule via `DEADWALL_UI140_BASELINE` : `reports/1.40.0/ui140-baseline139.log`. Cette référence échoue sur **6 scénarios**, tandis que le contrôle de focus extérieur passe. Après correction, **81/81 tests ciblés** passent, sans ignorés : les sept scénarios nouveaux et les régressions d’interface/monde sont dans `reports/1.40.0/ui140-final-targeted.log`. Les différences des trois fichiers runtime sont dans `reports/1.40.0/ui140.diff`. La vérification globale `npm run check` relève du contrôle final de livraison.

Aucune feuille CSS n’a été modifiée. Le contrôle d’installation confirme l’absence du CLI `agent-browser` dans cette session ; aucune session de navigateur n’a été ouverte. Les résultats concernent le DOM simulé et la cascade CSS statique existante, sans certification de CSS interactif, tactile matériel, audio ou FPS GPU.
